## システムパフォーマンス分析

負荷試験と一括りにされがちですが、実は様々な考え方や切り口があると思います。この記事では1段階解像度を下げて「システムパフォーマンス分析」として考えます。  

### マイクロベンチマーク

単純なワークロードを用いて CPU、メモリ、ディスク、ネットワークといった特定のコンポーネントや、特定のシステムコール、I/O オペレーションのみをターゲットとするテストです。  
マイクロベンチマークの優れた特性は以下の通りです。  

- デバッグと理解が容易：関与するコンポーネントやコードパスが最小限に絞られているため、テスト結果を容易に理解できます。
- 高い安定性と反復性：他のコンポーネントの干渉（摂動）が極力取り除かれているため、結果が安定しており、異なるシステム間でも公平に比較・反復できます。
- 根本原因への迅速な到達：パフォーマンスの違いが、どのハードウェアやソフトウェアの挙動に起因しているかを素早く特定できます。
- 現実との混同が起きにくい：最初から人工的なテストとしてデザインされているため、「これが現実世界のワークロードそのものである」という誤解を生みにくい性質があります。

### 晴れの日と雨の日

マイクロベンチマークには「晴れの日」と「雨の日」と呼ばれるパフォーマンステスト手法があります。  

晴れの日のパフォーマンステストは、理想的な環境での最高速度測定です。システム的に競合や干渉が一切無く、すべてのリソースが理想的な条件で動作する環境下で行うテストです。
システムの理論上の最高性能を測定してベースラインを把握することに向いています。  

雨の日のパフォーマンステストは、現実の悪条件を想定したストレス耐性測定です。最高性能の裏に隠れたシステムの脆弱性や本当の限界を見落とさないために、意図的に望ましくない過酷な条件を与えて行うテストです。
例えば、複数の処理が CPU を取り合うような条件を再現します。本番環境で問題が発生するのはこの「雨の日」です。悪条件でのパフォーマンステストも欠かしてはいけません。

晴れの日と雨の日の両方のパフォーマンステストをバランス良く実施することが大切です。

### マクロベンチマーク

クライアントがアプリケーションに要求を発行するような、現実的なワークロードをシミュレートしてシステム全体をテストするアプローチです。
レーシングカーに例えると、マイクロベンチマークがファクトリーでのテストなのに対し、マクロベンチマークは実際のサーキットで走らせるテストです。

マクロベンチマークのメリットは、マイクロベンチマークでは測定できない複雑なシステムコンポーネント同士の相互作用の効果を調査可能になる点です。
EC サイトであればマーケティング強化期間の突発的なワークロードをシミュレートするようなテストです。

マクロベンチマークを実装する手法は大きくわけて2パターン考えられます。  

1. シミュレーション
   1. 本番環境のワークロード特性（例：読み出し40%、書き込み7%、属性取得19%といったオペレーションの割合）を分析し、それに合わせて擬似的な負荷を生成します。
   2. パフォーマンステストツールを使うと機械的な負荷になりがちで、問題を発見しきれないことがあるので注意です。
2. リプレイ
   1. 本番環境で実際にキャプチャしたリアルなクライアント操作の「トレースログ」を、テスト対象のシステム上でそのまま流し込んで再生するアプローチです。
   2. 時間経過と共にオペレーションも変化します。古い操作キャプチャを長期間使い続けるのは危険です。


## サニティチェック

テスト結果のサニティチェックを行います。  
サニティチェックとは、ベンチマークの結果に何かおかしな部分が含まれていないかどうかを確認する作業です。

例えば、ネットワーク経由のファイルコピーテストを実施したとして、合格基準を超える結果が出たとします。しかし、よく計算してみるとネットワーク帯域幅を超えた結果が出ることがあります。どこかでキャッシュが効いていたり、ツールの測定方法に問題があるケースです。
サニティチェックを通じて数値の不自然さに気づき、そこから新たな仮説や予測を立てて確認テストを行うことで、誤ったベンチマーク結果によってシステム評価やキャパシティプランニングを誤るリスクを回避します。現代であれば LLM にサニティチェックを依頼すると良いでしょう。

サニティチェックによって数値の矛盾に気づくことは、単に「テストが失敗した」と落胆することではありません。そこから「なぜこの不自然な数値が出るのか」という新たな仮説を立て、追加の観察や可観測性ツールによるダブルチェックを行い、システムやツールの真の挙動を深く理解するための第一歩となります。

## テストシナリオ

効果的なシナリオを作成します。どこに律速があるかでシナリオが変わります。律速は1つではないことがあります。それぞれの律速に合わせた複数のシナリオを作成します。

測定対象を間違えないためにもシナリオを正確に作ります。

- キャッシュを考慮する
  - モダンアーキテクチャは至るところにキャッシュが存在します。キャッシュを意図的にコントロールしたシナリオを作ります。
- エラーを正しく扱う
  - 通信エラー・処理エラーにより処理時間が極端に良くなる or 悪くなることがあります。これを通常の処理結果に含めず、除外するようにします。
- 平均的な負荷に留意する
  - ツールを使い負荷を発生させると平均的になりがちです。秒間1000req と設定したとします。しかし、本番環境でそのような均等なリクエストが来ることは稀です。強力なバーストを考慮した「波」を発生させます。
- 晴れの日と雨の日の両方をカバーする
- 限界テスト時はランプ負荷をかける
  - 一気に負荷をかけるのではなく、徐々にリクエスト数を増やしていきます。こうすることで、ニーポイント (限界境界) が特定できます。
- 測定ブレを防ぐ
  - テストを複数回実行し、標準偏差が少ないことを確認します。標準偏差が大きい場合はそのテスト結果は採用しません。
  - 長時間のテストを実行します。数秒では偶発的要因のブレが発生します。
- ユーザー目線
  - 最も大切です。ユーザーにとって許容可能な範囲はどこなのかを探索することに重点を置きます。

## やったこと

前述したことをふまえて、実際のテスト作業を振り返ってみます。

### テスト対象の洗い出し

今回は我々のプロダクトの一部 API がテスト対象です。LLM にお願いしてソースコードからテスト対象一覧を洗い出します。

| No | Method | パス | 説明 |権限 |負荷の重さ |
| --- | --- | --- | --- | --- | --- |
| 1 | GET |/connections | 自分のユーザー接続一覧＋利用可能クライアントを取得 | 閲覧系 | 中（複数クエリ） |
| 2 | GET | /clients | 登録済みクライアント一覧を取得 | 管理者系 | 中（複数クエリ） |
| 3 | POST | /clients | クライアントを新規作成 | 管理者系 / audit | 重い（外部OAuth2交換, 30s timeout）|
| 4 | GET | /clients/{client_id} | クライアント1件の詳細を取得 | 管理者系| 軽量（単件）|
| 5 | GET | /providers | 利用可能なプロバイダー一覧を取得 | 管理者系 | 軽量 |

Read と Write はそれぞれシナリオを作るので Method を表示してくれるのはありがたいです。`負荷の重さ` は負荷のかけ具合とテスト結果の正確さチェックに使えます。

### テストシナリオ作成

シナリオも LLM に作成してもらいます。プロンプトをそのまま書くと事故になりそうなのでポイントだけ。正確なシナリオを生成するために心がけたことです。

- ソースコードを読ませ、有意なシナリオを作ってもらう
- 前提条件を示す
  - 障壁になることを明示
  - 外部 API を利用する場合は、外部 API の制限を伝える
- サニティチェックを行う
  - 「平均」でなく percentile と分布全体（標準偏差・変動係数）で評価する
  - HTTP 429/5xx で短時間バーストしていないか
  - シンプル Read の結果が線形に伸びているならインフラリソースを使い切っていない
  - パフォーマンスが非現実的に良く p95 が平坦なら何かの処理を素通りしている可能性あり
- 留意点を明示する
  - 安定したペースでばかりリクエストを送らないよう注意
  - 現実世界のワークロードの「ばらつき」を意識
    - キューが溜まったときにどう変化するか？
    - リソース使用率が 60% を超えたときにどう変化するか？
  - 負荷（リクエスト数）に対するスループットやレイテンシの変化をグラフ化し、パフォーマンスの伸びが頭打ちになる「ニーポイント」を特定することが重要
  - 「平均値」の過信を避ける
  - パーセンタイルと分布全体を評価する
  - 標準偏差や変動係数による「ばらつき」の評価

----

また、律速がどこにあるかで計測するものが変わります。律速 x 経路ごとにシナリオを作ります。それによって優先度も決まります。

|  | 内部 律速 | 外部 API 律速 |
| --- | --- | --- |
| read（GET 系） | トラック A（本命） | 該当なし |
| write（CRUD） | トラック B（optional） | トラック W-real |

**優先度: A ＞ W-real ＞ B**

- **A**: 低コスト（mock 不要）× 高頻度エンドポイント。「実運用トラフィック」に直接答える本命。
- **W-real**: 外部 API での CRUD 運用実態と外部 API 律速点。本番運用でも使用されるので運用上の意味がある。
- **B**: 内部の write 容量。ただし network mock が要り対象も低頻度な管理者操作なので優先度は低い。

### テストプログラム作成

これは LLM の得意分野です。
テストツールを指定したうえでシナリオを読み込ませ、テストプログラムを作成します。  
大切なのは、テスト開始〜完了までの詳細ログをテキストファイルで残しておくことです。こうすることでテスト結果の精度が向上します。もちろん、結果集計をするのは LLM なのでログは多少難解でも大丈夫です。  
ここは割愛しましょう。

### テスト結果

テストプログラムの詳細ログを LLM で分析し、テスト結果を出力します。

#### 総合判定

各トラックの詳細記録を元に総合判定をしてもらいました。  
ニーポイントの特定ができています。テスト結果が良好すぎて疑わしいところも判別できています。

| トラック | フェーズ | 設定 | 判定 | 根拠 |
| --- | --- | --- | --- | --- |
| **W-real** | 平常時 ×5 | 1VU×20iter | ✅ 期待通り | 失敗 0%、create p95 674ms（update込み 924ms）、delete p95 206ms。閾値内 |
| **W-real** | ピーク ×5 | 12VU×60s ／ 6VU×60s(upd) | ✅ 期待通り | 失敗 0%、checks 100%、create p95 811ms < 10s、delete p95 322ms < 1.5s。exit 0 |
| **W-real** | 限界（ランプ） | `1m:8,2m:16,2m:24` | ✅ **外部 API 429 点を特定** | 直近60秒窓 create ≈1,060/min（16→17VU、t=197s）で 429 発生 — 外部 API 仕様 1,000 req/min/user と一致 |
| **A** | 平常時 ×5 | 10VU×60s（connections / clients） | ✅ 期待通り | 失敗 0%、p95 371〜406ms < 800ms。exit 0 |
| **A** | ピーク ×5 | 100VU×60s（providers） | ⚠️ 閾値超過 | エラー 0%（全200）だが p95 6,434ms ≫ 800ms → 全5回 exit 99。**100VU はニーポイントの遥か先** |
| **A** | 限界（plateau 探索） | 8〜40VU×90s（clients） | ✅ **ニーポイント特定** | **knee ≈ 20VU / 71 req/s**（限界スループット感度が 20→24VU で +2.3→+0.5/VU に急落、p95 が 20VU の 598ms から 24VU で閾値 800ms 帯へ）。天井 ≈78 req/s、ACA CPU 律速。fail 0% |

#### 留意点への対応

指示していた留意事項に対しても分析を行ってテスト自体の確からしさを保証します。

| 留意点 | 状況 |
| --- | --- |
| 安定ペースのみで送らない | ✅ closed-model の自己調整＋平常/ピーク/ランプの 3 負荷帯で変動。⚠️ ただし arrival-rate 固定・バースト注入は未実施 |
| キューが溜まったときの変化 | ✅ A ピークで実測: シェディングせずレイテンシで吸収（エラー0・p95 16倍） |
| リソース 60% 超の変化 | ✅ ACA CPU 78% でスループット頭打ち＋テール爆発を確認 |
| ニーポイントのグラフ化・特定 | ✅ W-real: 外部 API 429 点 ≈1,000 create/min を特定 ／ ✅ A: plateau 探索で **knee ≈ 20VU / 71 req/s**・天井 ≈78 req/s・ACA CPU 律速を特定 |
| 平均値の過信を避ける | ✅ A ピークで平均 1.53s vs med 0.44s（3.5倍乖離）を明示 |
| パーセンタイル・分布全体 | ✅ med/p90/p95/max を全フェーズで記録。二峰性・テールを確認 |
| 標準偏差・CV | ✅ run 間 CV 1〜8%（再現性高）。W+update の create p95 CV 49.6% は単発テール由来 |

## まとめ

パフォーマンステストはプロジェクト工程の後半の後半に計画・実施されることが多く、ともすれば単なる「確認作業」になりがちです。  
担当者は十分に検討して実施した、しかし、本番運用が始まったらパフォーマンスで悩まされるということは珍しくありません。
シナリオの網羅性、サニティチェック、晴れの日ばかりでパフォーマンステストをしているなど原因は複数で様々だと思いますが、それでは努力も報われません。
期待通りのテストと結果を得るために基本を身に付けることができました。
