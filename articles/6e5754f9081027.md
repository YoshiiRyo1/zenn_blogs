こんにちは。  
ご機嫌いかがでしょうか。  
"No human labor is no human error" が大好きな[吉井 亮](https://twitter.com/YoshiiRyo1)です。  

システムの健全性を測る方法は何種類かあると思います。
可用性の測定、性能の測定、エラー監視、リソース使用率、外形監視・合成監視、データの検証、障害からの回復力などが思い浮かびます。「利用者が正常に使えるか」と「内部に異常の兆候がないか」を組み合わせて考えることが多いと思います。そこから SLO/SLI の設計にまで発展させて運用設計・実装しているシステムもあると思います。

今回考えるのは合成監視です。Synthetic Monitor とも言います。
ログイン → 商品検索 → カート追加 → 購入のようなユーザーの行動を模してテスト実行し、その結果を数値化してシステム健全性を測ります。
合成監視の利点は何と言っても「ユーザーが実際にその機能を利用していなくても、不具合を検知できること」でしょう。
リクエスト成功率、レスポンスタイム、エラー率といった「実際に発生した行動」を観測しているだけでは、利用頻度の低い機能の不具合を事前に検知するのは難しいものです。合成監視をフル活用してこれを検知します。

## カナリアの導入フロー

### テストケースの作成

最も重要なステップです。
ユーザーが達成したい動線は何でしょうか？ それを第一にテストケースを考えます。 EC サイトで例えると「商品を購入」だけではなく「検索 〜 商品選択 〜 カート追加 〜 決済 〜 購入履歴閲覧」までを含めます。

自身のプロダクトに備わっている全機能を漏れなく通るようなテストケースを考えます。代表的な機能だけではなく、利用頻度が低い機能も忘れずに対象に加えます。ソースコードを解析させて LLM にテストケースを提案させることが効果的です。過去のインシデント情報を LLM に与えることも有用です。ただ、開発者による最終確認は必須です。人間が必ず意図を持ってチェックしましょう。

それぞれのテストケースの依存関係や排他関係を把握しておきます。依存や排他によってテストが成り立たない事態を避けます。例えば、A で処理したデータが無いと B が空振りする、といったことです。この例ならば、テストスクリプトで A → B の順番に実施するよう強制します。

テストに使用するデータは繰り返し使えるようにしておくのがベターです。カナリアは時間起動で自動的に実施されます。都度データ加工をするとサイクルの長時間化や精度の低下につながります。

### テストスクリプト作成

テストケースとソースコードがあれば LLM に依頼するだけです。素晴らしい世界になりましたね。
テスト実行基盤には選択肢があります。管理しているシステムに合致した最適な基盤を選択しましょう。クラウドベンダーが提供している Synthetic Monitor サービスを使うとカナリア自体の運用コストは下がると思います。 FaaS やコンテナのタスク実行もあります。やむを得ない事情があれば VM でも構わないでしょう。
単純な HTTP レスポンスの確認だけではなく、マルチステップの複雑なブラウザ操作の検証を行うテストスクリプトを作成します。クラウドベンダーが提供している Synthetic Monitor サービスならそのような機能は実装されているはずですし、OSS のツール・フレームワークも多数存在します。テスト実行基盤と合わせて検討します。

テスト結果をどうやって可視化するのかを考えておきます。「成功 or 失敗」だけでは物足りません。スクリーンショットの保管や HAR ファイルの生成、デバッグログの出力、テレメトリシグナルの出力を実装して、**後から見て何が起きているか判断できる**状態にしておくことが望ましいと考えます。どこで何が起きているのか把握できるようにテストケースごとにこれらを保管・出力します。

テストスクリプトのちょっとしたテクニックを紹介します。カナリアで使うテストスクリプトをそのまま負荷試験に使えるようにしておくことをお勧めします。スクリプト実行時に環境変数によってモードを使い分けます。負荷試験モードの際は、多重度・並列度を上げてテスト実施可能な作りにするのです。負荷試験モードではスクリーンショットや HAR ファイルの保管を行わないようにしておきます。ログやテレメトリは出力したほうが良いでしょう。

### カナリアテストのオブザーバビリティ

何のためにカナリアテストを実施するか？ それは「健全性を測る」ためでした。
私はテストスクリプトから Datadog へ複数のテレメトリを送信しました。

- Count: `hoge.canary.sli.reports`、`hoge.canary.sli.passed`、`hoge.canary.sli.failed`、`hoge.canary.sli.unavailable`
- Distribution: `hoge.canary.sli.duration_ms`（`status` タグ付き）、`hoge.canary.sli.duration_ratio`

これらのテレメトリを基に以下の指標を観測しています。

| 指標 | 意味 |
| --- | --- |
| reports | 集計・送信対象となったシナリオ結果件数 |
| 成功率 | passed ÷ reports |
| 失敗率 | failed ÷ reports |
| unavailable | 未実行・skip・中断・結果欠落 |
| p50／p90／p99 | 有効な所要時間を Distribution として送信した標本の分位値 |

    - 直近1週間
    - 直近24時間
    - 直近4時間
- シナリオ別の実行件数・成功率・レイテンシー
  - Canary 名
  - LATENCY P99
  - LATENCY P90
  - LATENCY P50
  - 報告件数
  - サンプル数
  - 計測不能件数
  - 失敗率
  - 成功率
- 実行の健全性と詳細推移
  - healthy: 選択期間内の最新値。1=全対象シナリオが成功し、補助テスト・後片付け・レポートにも異常なし。0=いずれかに問題あり。サービス可用性 SLO ではない。
  - expected: 選択期間内の最新の実行対象シナリオ数。認証・preflight などの補助テストは含まない。passed + failed + unavailable と比較する。
  - passed: 選択期間内の最新 run で成功した対象シナリオ数。意図したエラー挙動の検証成功も含む。
  - failed: 選択期間内の最新 run で失敗した対象シナリオ数。
  - unavailable: 選択期間内の最新 run で計測不能だった対象シナリオ数。未実行・skip・中断・結果欠落などを含み、成功とは扱わない。
  - supporting_ok: 選択期間内の最新値。1=認証・preflight などの補助テストがすべて成功。0=補助テストの失敗または結果なし。
  - cleanup_failed: 選択期間内の最新値。1=テストの後片付け失敗が報告された。0=報告なし。0でも残存データが一切ないことは保証しない。
  - report_available: 選択期間内の最新値。1=集計に使う Playwright レポートの suites 配列が存在する。0=取得不能。1でも全シナリオの結果が揃っているとは限らない。
  - Critical outcomes（成功・失敗・計測不能の推移）: 成功・失敗・計測不能の対象シナリオ数の推移。グラフの欠測は成功を意味しないため、GitHub Actions の実行・待機状態と送信結果を確認する。
  - Suite duration (ms): Playwright が記録したテスト実行全体の所要時間（ms）の推移。認証・補助テストを含むが、Actions のキュー待ちや依存関係インストール時間は含まない。 
  - シナリオ別の実行時間（ms）: シナリオごとの実行時間（ms）の推移。テスト全体の所要時間であり、業務処理単体の時間や p95 ではない。表示期間によっては同じ時間バケット内の複数 run が平均される。日本語名未登録のシナリオは canary ID で表示する。retired のシナリオは系列を出さず、ID での再表示も抑止する。
  - シナリオ別の成功（1: 成功 / 0: 失敗）: シナリオごとの結果の推移。1=成功、0=失敗。時間バケット内の平均で中間値になる場合がある。計測不能は欠測になり、unavailable で確認する。retired のシナリオは系列を出さず、ID での再表示も抑止する。
- 共有リソース｜他の処理と取り合う基盤の負荷
  - コンテナ CPU 使用率
  - コンテナ メモリ使用率
  - コンテナ レプリカ数
  - キュー待ち
  - DB CPU 使用率
  - Redis サーバー負荷

## 今後やりたいこと

カナリアテストでエラーが多発するケースに関して、自動修正 PR の作成やロールバックを検討したいです。本番環境に不具合を持ち込む前に阻止したい意図です。
